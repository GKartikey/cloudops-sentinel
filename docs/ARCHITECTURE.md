# Architecture

## The problem this solves

Three questions get asked about every cloud estate, usually by three different
people, and they are almost always answered by three different tools that
disagree with each other:

| Question | Asked by | Usually answered by |
|---|---|---|
| Is it working? | On-call engineer | Monitoring / APM |
| Is it going to keep working? | SRE / platform team | Capacity and reliability review |
| Why does it cost this much? | Engineering manager, finance | A billing export, weeks later |

CloudOps Sentinel answers all three from **one telemetry pipeline**. That is the
central design decision, and everything else follows from it. Utilisation is not
just a reliability signal — it is the numerator of the cost-efficiency
calculation. A box at 6% CPU is simultaneously a healthy resource, a capacity
risk of a different kind, and $1,053 a month of waste. Splitting those views
across separate tools is what lets an organisation argue about whose number is
right instead of fixing the problem.

## Constraint: it must run on a laptop

The hard requirement was zero cloud spend. The naive approach — mock everything —
produces a demo that proves nothing, because the detection logic is fed the
answers. The approach taken here splits the estate in two:

```
                    ┌──────────────────────────────────────────┐
                    │            SIMULATED HALF                │
                    │  16 Azure + AWS resources from a YAML    │
                    │  inventory. Telemetry is generated by a  │
                    │  deterministic model. Gives breadth:     │
                    │  RDS, S3, Lambda, load balancers,        │
                    │  orphaned disks, regions, tags, SKUs.    │
                    └──────────────────────────────────────────┘
                                       +
                    ┌──────────────────────────────────────────┐
                    │              LIVE HALF                   │
                    │  3 real Docker containers. CPU/memory    │
                    │  read from their own cgroup. Scraped     │
                    │  over HTTP. Chaos genuinely burns CPU,   │
                    │  leaks memory, returns 500s, or exits    │
                    │  and gets restarted. Gives truth.        │
                    └──────────────────────────────────────────┘
```

Everything above the collector treats both identically. The health scorer, the
anomaly detector, the alert engine and the cost model cannot tell which is
which — they only ever see a `Resource` and a stream of samples. That is what
makes the demonstration honest: when a real container is pushed to 94% CPU, the
alert that fires was not told an incident was requested. It worked it out from
the measurements, over the network, like any other target.

## The collection loop

One tick, every `COLLECT_INTERVAL_SECONDS` (default 10):

1. **Expire incidents.** Anything past its end time is closed automatically, so
   a demo cannot leave the fleet wedged.
2. **Generate** samples for the simulated resources, applying any active
   incident modifiers.
3. **Scrape** the live containers concurrently (`asyncio.gather`). A failed
   scrape is recorded as `availability=0`, not skipped — *down is a measurement*,
   and skipping it would make a dead target indistinguishable from a healthy one
   the alert rules never matched.
4. **Persist** samples and logs in two batched writes.
5. **Analyse**: score health, run both anomaly detectors, evaluate alert rules.
6. **Publish** every value as a Prometheus gauge.
7. **Prune** past the retention window, roughly once a minute.

The loop is wrapped in a bare `except` that logs and continues. A monitoring
system whose collector dies on one malformed sample is worse than no monitoring
at all, because everyone assumes silence means health.

### Pull, not push

Targets do not push to the control plane; the control plane scrapes them. This
is the Prometheus model and it is chosen for one specific property: **a target
that dies is detected by its absence.** With push, a silent target and a healthy
target look identical until someone notices the dashboard has stopped moving.

### No Docker socket

Restart counts are derived by watching each target's reported process start
time change, and cross-checked against a counter the container persists across
restarts. The obvious alternative — mount `/var/run/docker.sock` — hands the
monitoring container root on the host. A restart counter is not worth that
trade. See [SECURITY.md](SECURITY.md).

## Why these engineering choices

| Choice | Alternative | Why |
|---|---|---|
| SQLite (WAL) | Postgres/Timescale | Must run on a laptop with no managed DB. Write rate is a few hundred rows per tick. The access pattern — append-only series plus small mutable tables — ports upward unchanged. The cost is single-writer, recorded in [LIMITATIONS.md](LIMITATIONS.md). |
| Robust z-score (median + MAD) | Mean + stdev, or ML | Explainable at 3am, no training job, cold-start safe. One outlier inflates a stdev enough to hide the next real anomaly — the exact failure robust statistics exist to prevent. |
| Deterministic simulator | `random.gauss` per sample | `value(resource, metric, t)` is a pure function, so the 6-hour backfill is continuous with live samples and the demo reproduces exactly. White noise would also make every detector look brilliant for the wrong reason. |
| Rule-based recommendations | ML sizing model | Every finding must show its evidence. "The model said so" does not survive review by the team that owns the resource. |
| Vanilla-JS dashboard | React + charting lib | No build step, no CDN, no npm dependency tree bolted onto a security tool. Works air-gapped. |
| One aggregate `/overview` | 8 endpoints per refresh | The dashboard polls every 5s; 8 requests per refresh multiplies load for no benefit. |

## Data model

```sql
samples(ts, resource_id, metric, value)          -- append-only time series
logs(ts, resource_id, service, level, message, context)
alerts(fingerprint PK, rule, resource_id, status, value, first_seen, ...)
alert_history(ts, fingerprint, event, ...)       -- audit trail
anomalies(ts, resource_id, metric, value, baseline, score, method, ...)
incidents(id PK, scenario, resource_id, started_at, ends_at, status, ...)
```

Alert state lives in the database rather than in memory, so it survives a
restart of the control plane. An alerting system that forgets everything when it
is redeployed will forget it during the deploy that caused the incident.

The alert **fingerprint** is `rule:resource_id` — stable, so one ongoing problem
updates one row instead of accumulating thousands.

## Request path

Every request gets a correlation ID (generated, or honoured from
`x-correlation-id`), carried in a `ContextVar` so every log line emitted while
serving it can be joined afterwards. The middleware records RED metrics labelled
by **route template**, not raw path — `/inventory/{resource_id}` is one label
value; the raw path would mint one series per resource and eventually take
Prometheus down.

## Extending to a real cloud

The only module that changes is `engine/inventory.py`. Replace `load_inventory`
with a function that calls the Azure Resource Graph or the AWS Resource Groups
Tagging API and returns the same `Resource` objects. Everything downstream keeps
working, because nothing downstream knows where the estate came from.

For real telemetry, point the collector at Azure Monitor / CloudWatch instead of
the simulator, and replace the hand-rolled rate card in `config/pricing.yaml`
with the Azure Retail Prices API or the AWS Price List API. Both are documented
in [COST_MODEL.md](COST_MODEL.md).
