# Security and least privilege

Every claim in this document is asserted in CI by the `k8s-validate` job. A
future edit that drops `runAsNonRoot`, adds an RBAC wildcard, grants a
monitoring identity access to secrets, or commits a literal credential fails the
build. Documented policy that is not enforced is a comment.

## 1. No hardcoded credentials

There is no credential anywhere in this repository. Not a placeholder that
works, not a default, not a test fixture.

| Secret | Source | Behaviour when unset |
|---|---|---|
| `CLOUDOPS_API_TOKEN` | env var, from a K8s Secret or `.env` | API is unauthenticated, and `/readyz` and `/api/v1/system` **say so** (`auth_enabled: false`) |
| `ALERT_WEBHOOK_URL` | env var | The webhook sink is not registered at all. There is no fallback endpoint. |
| Grafana admin password | Docker secret from `secrets/grafana_admin_password.txt`, gitignored, generated by `make secrets` | Grafana falls back to its own first-run credential and forces a change |

Two design points worth defending:

**Unset means absent, not default.** `WebhookSink` is only constructed if a URL
is present. A misconfigured deployment cannot silently post alerts to somebody
else's endpoint because a default was left in the code.

**An unauthenticated deployment admits it.** The readiness payload reports
`auth_enabled`. A demo without a token is fine; a demo that *looks* secured
while being open is how a laptop deployment gets promoted to a shared
environment by mistake.

The Grafana password reaches the container via `GF_SECURITY_ADMIN_PASSWORD__FILE`
and a Docker secret rather than an environment variable, because environment
variables are visible in `docker inspect` output to anyone on the host.

### Token comparison

```python
hmac.compare_digest(expected, presented)   # not ==
```

`==` on strings short-circuits at the first differing byte, so response timing
leaks how many leading characters were right and the token can be recovered one
character at a time. Constant-time comparison closes that.

### Split read/write authorisation

`REQUIRE_TOKEN_FOR_WRITES=true` keeps `GET` open — a dashboard on a wall in the
office — while incident injection and alert acknowledgement still require the
token. Least privilege applied to an HTTP surface: the read path and the
state-changing path have genuinely different risk, so they get different
requirements.

## 2. Container hardening

Both images:

- **Multi-stage build.** Dependencies are compiled in a builder stage; the
  runtime stage copies only the virtualenv and the source. Build tools, pip
  caches and package indexes never ship. Smaller image, smaller attack surface,
  fewer CVEs to triage.
- **Non-root, fixed UID 10001.** Root in a container means a container-escape
  bug is a root-on-host bug. A fixed non-zero UID also lets the Kubernetes
  `securityContext` pin `runAsUser` to a known value.
- **`cap_drop: ALL`** and **`no-new-privileges`** — a process cannot acquire
  capabilities it was not started with, closing the setuid escalation path.
- **`HEALTHCHECK`** using stdlib `urllib`, so no `curl` needs to be in the image.
- **Exec-form `CMD`**, so the application is PID 1 and receives `SIGTERM`
  directly. Shell form leaves `/bin/sh` as PID 1 swallowing the signal until the
  grace period expires and the process is killed outright — losing the clean
  shutdown path.

In Kubernetes, additionally: `readOnlyRootFilesystem: true` (with explicit
`emptyDir` mounts for `/tmp` and `/state`), `allowPrivilegeEscalation: false`,
`seccompProfile: RuntimeDefault`, and the namespace enforces the
**`restricted`** Pod Security Standard with `warn` and `audit` set alongside
`enforce` — so a violation is visible to the person applying it and in the audit
log, not just silently rejected.

## 3. RBAC and least privilege

### Every workload has its own identity

Nothing uses the `default` ServiceAccount. Sharing it means every pod in the
namespace inherits every permission any one of them needs, and a permission
granted that way can never be taken back without auditing every workload.

### No token where none is needed

```yaml
# cloudops-demo ServiceAccount
automountServiceAccountToken: false
```

The demo workloads never call the Kubernetes API, so they do not get a token. A
token that is not mounted cannot be read out of the filesystem by an SSRF or a
path-traversal bug.

### Role, not ClusterRole. Verbs, not wildcards.

The control plane gets a namespaced `Role` with `get`, `list`, `watch` on pods,
services, endpoints, configmaps, deployments, events and pod metrics.

What it is deliberately **not** granted:

- **`secrets`** — a monitoring component that can read secrets can read every
  credential in the namespace. No dashboard is worth that. CI fails the build if
  `secrets` appears in any rule.
- **`create` / `update` / `delete` / `pods/exec`** — a read-only identity that
  can also create pods is a direct privilege-escalation path to cluster-admin
  (create a pod that mounts a privileged service account, done).
- **`*`** on verbs or resources, ever.

One `ClusterRole` exists, because node objects are cluster-scoped and genuinely
cannot be granted with a `Role`. It is confined to reading nodes and node
metrics, and nothing else.

### Network policy: default deny

Kubernetes networking is flat by default — every pod can reach every other pod
in the cluster, so one compromised container can scan the entire estate. The
manifests invert this:

1. `default-deny-all` — empty pod selector, both directions, no rules.
2. `allow-dns-egress` — the exception everyone forgets. Without it every pod
   hangs on name resolution with an error that looks nothing like a network
   policy problem.
3. Control plane → workloads on TCP 8080, one direction only.
4. Ingress to the control plane from the `monitoring` and `ingress-nginx`
   namespaces, plus same-namespace debugging.
5. Egress to the internet restricted to TCP 443 and **excluding
   `169.254.0.0/16`**.

That last exclusion is the important one. `169.254.169.254` is the cloud
instance metadata endpoint — it is how a server-side request forgery bug turns
into stolen IAM role credentials. Blocking it at the network layer means the
application code is not the only thing standing between a bug and a cloud
credential.

> **Verify enforcement.** Network policies require a CNI that implements them
> (Calico, Cilium, Azure CNI with policy, AWS VPC CNI + Calico). On a CNI that
> ignores them these objects apply cleanly and do *nothing*, which is a
> genuinely dangerous illusion of security. Test it with a deny-check, do not
> assume it.

### Preferred: no secret in the cluster at all

The `cloudops-secrets` manifest ships with **empty** `stringData` on purpose, so
applying it creates an empty Secret rather than a working credential shared by
everyone who ever cloned the repository. Create the real one out of band:

```bash
kubectl -n cloudops create secret generic cloudops-secrets \
  --from-literal=CLOUDOPS_API_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
```

Better still, remove it from Kubernetes entirely:

- **Azure** — Workload Identity + Key Vault CSI driver
- **AWS** — IRSA + Secrets Manager / Parameter Store CSI driver
- **Either** — External Secrets Operator syncing from the cloud secret store

A secret that is never written into etcd cannot leak out of etcd. Kubernetes
Secrets are base64, not encryption; without an `EncryptionConfiguration` they
are plaintext at rest.

## 4. Supply chain and CI

- `GITHUB_TOKEN` with job-scoped `packages: write` — no long-lived PAT stored as
  a repository secret, nothing to rotate or leak. Default permissions are
  `contents: read`; every job opts in to more.
- Publishing runs **only** on a push to `main`, never on a pull request, so a
  fork PR cannot push an image.
- Trivy scans the images and the filesystem; results go to the GitHub security
  tab as SARIF.
- **Secret scanning is a hard failure** (`exit-code: 1`), while base-image CVEs
  are not. That asymmetry is deliberate: a committed credential is always
  actionable, whereas failing the build on an unfixable base-image CVE produces
  a permanently red pipeline that everyone learns to ignore — and then they
  ignore the real one too.
- Images are pushed with SBOM and build provenance, so a running image can be
  traced to the commit and workflow run that produced it.
- Dependencies are pinned to exact versions in `requirements.txt`, and the CI
  actions are pinned to major versions.

## 5. Application-level hardening

- **CSP-friendly dashboard.** No inline event handlers, no CDN, no `eval`. All
  API data is inserted with `textContent`, never `innerHTML`, so a resource name
  or a log message can never become executable script.
- **Response headers**: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`.
- **Input validation** at the edge via Pydantic: incident duration is bounded to
  30–3600s, magnitude to 0.1–3.0, note length capped, `status` and `level`
  filters constrained by regex. Every list endpoint has a maximum `limit`, so no
  request can ask the service to materialise the entire retention window.
- **Parameterised SQL everywhere.** No string interpolation of user input into a
  query.
- **Config mounted read-only** (`./config:/app/config:ro`). The control plane
  has no business rewriting its own inventory or rate card at runtime.
- **Secrets are never echoed.** `/api/v1/system` returns
  `Settings.redacted()`, which converts credentials to booleans
  (`auth_enabled`, `alert_webhook_configured`). Verified by the e2e script.

## 6. The deliberate exception

`POST /admin/chaos` on the demo services is a genuine remote code-effect
endpoint: it makes a container burn CPU, leak memory, return errors, or exit.

It exists because inducing real failure is the entire point of the
demonstration, and a fake incident would prove nothing about the detection path.
It is documented here rather than left as an accident. In a real deployment it
would be removed at build time, or bound to a separate port that is not exposed
outside the cluster and sits behind authentication. The network policy already
restricts who can reach the workloads on 8080 to the control plane alone.

Nothing analogous exists on the control plane. Its only state-changing endpoints
are incident orchestration and alert acknowledgement, both behind
`REQUIRE_TOKEN_FOR_WRITES`.

## Threat model summary

| Threat | Mitigation |
|---|---|
| Container escape → host root | Non-root UID 10001, all capabilities dropped, no-new-privileges, seccomp, read-only rootfs |
| Stolen API token via timing | `hmac.compare_digest` |
| Credential in version control | No credential exists; Trivy secret scan fails the build |
| Lateral movement after compromise | Default-deny NetworkPolicy, single permitted east-west path |
| SSRF → cloud credential theft | Link-local `169.254.0.0/16` excluded from egress; no metadata access needed |
| Privilege escalation via RBAC | Namespaced Role, read verbs only, no `secrets`, no `create`, no wildcards; asserted in CI |
| Stolen SA token from a workload | `automountServiceAccountToken: false` on workloads that do not need it |
| XSS via a resource name or log line | `textContent` only, no `innerHTML`, no CDN |
| Malicious/oversized API input | Pydantic bounds, regex-constrained filters, hard `limit` caps |
| Log injection | Structured JSON logging; message and context are separate fields |
| Supply chain | Pinned dependencies, multi-stage build, SBOM + provenance, image scanning |
